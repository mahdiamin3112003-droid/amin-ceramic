# 0009 · `uuid_generate_v7()` in SQL, because `pg_uuidv7` is not on Supabase

**Status:** accepted · Phase 0

## What the document says

`docs/03-database-design.md` §0.1 revision 2 chooses **UUIDv7** for domain
entities:

> Time-ordered, so it has the index locality of a sequential key while remaining
> globally unique — which matters for the multi-tenant path, for
> offline-generated IDs in the ingestion pipeline, and for not leaking row counts
> in public URLs.

§0.4 then lists `pg_uuidv7` among the required extensions.

## The problem

`pg_uuidv7` is not in Supabase's available-extension catalogue. `pgcrypto`,
`citext`, `vector`, `pg_trgm`, `unaccent`, `btree_gin`, `pg_cron` and
`pg_stat_statements` all are; that one is not. A migration that assumes it would
fail on the target platform.

## Decision

Ship a pure-SQL `uuid_generate_v7()` built on `pgcrypto`. Same RFC 9562 layout,
same ordering guarantees, no extension dependency — and it behaves identically
on a local Postgres, which matters for CI and for developers without a Supabase
project.

```sql
CREATE OR REPLACE FUNCTION uuid_generate_v7()
RETURNS uuid LANGUAGE sql VOLATILE PARALLEL SAFE AS $$
  SELECT encode(
    set_bit(set_bit(
      overlay(uuid_send(gen_random_uuid())
              PLACING substring(int8send(
                floor(extract(epoch FROM clock_timestamp()) * 1000)::bigint
              ) FROM 3)
              FROM 1 FOR 6),
      52, 1), 53, 1),
    'hex')::uuid;
$$;
```

It takes a v4 UUID for its random bits, overlays the first 48 bits with a Unix
millisecond timestamp, then flips the version nibble from `0100` (v4) to `0111`
(v7). Postgres numbers `bytea` bits LSB-first within each byte, so the version
nibble of byte 6 is bits 52–55 and setting 52 and 53 performs that flip.

**Decision of record #3 in `docs/03` is unchanged.** Only the mechanism differs.

## Consequences

If `pg_uuidv7` turns out to be available on the provisioned project, switching is
a one-line migration: `CREATE EXTENSION pg_uuidv7` and drop this function. The
column defaults do not change, because the function name is the same.

Postgres 18 has a native `uuidv7()`. When Supabase offers it, this becomes a
one-line alias.
